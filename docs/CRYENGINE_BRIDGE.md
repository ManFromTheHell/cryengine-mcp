# CryEngine bridge — editor API reference

Generated by introspecting the running Sandbox Python interpreter: 586 functions in 24 modules (`editor_api.json`), plus the 7 functions of the plugin's own `SandboxBridge` module listed below (593 across 25 in total). Regenerate with the snippet at the bottom rather than editing by hand.

## The three registries

Sandbox has three *separate* command registries. Picking the wrong one returns `Unknown command` for a command that genuinely exists — this is the single most common way to waste time here.

| Registry | Bridge tool | Holds |
|---|---|---|
| Python interpreter | `execute_python` | The 593 `module.function` calls listed below. **The widest surface — prefer it.** |
| `ICommandManager` | `execute_editor_command` | `module.command` names registered with `REGISTER_EDITOR_AND_SCRIPT_COMMAND` / `REGISTER_PYTHON_COMMAND`. A subset of the above. |
| `IConsole` | `run_console_command` | CVars and true console commands (`r_DisplayInfo 1`, `e_TimeOfDay 12`). Knows nothing about `module.command` names. |

`run_console_command` is also the escape hatch for the plugin's own `bridge.*` verbs: the plugin matches the raw command text before falling through to IConsole, so any `bridge.*` verb works through it even with no dedicated MCP tool.

## Gotchas that cost real time

These were observed on CRYENGINE 5.7.1 and are field notes; verify them with the tools before relying on them.

**The bridge runs on the editor's idle tick.** Anything that blocks that tick freezes the bridge and every command times out:

- An **open menu** in Sandbox blocks it. If everything suddenly times out, check whether a menu is open.
- A **modal dialog** blocks it until a human clicks. Never call a dialog-opening command blind — see the list below.
- Sandbox must be **running with a level loaded**. With no level, `bridge.terrain.info` reports width/height 0 and layerCount 0.
- Focus-independence needs `ed_keepEditorActive` set to 1 while the editor is running (`run_console_command ed_keepEditorActive 0`, then `1`). The same value in `user.cfg` has no effect.

**`%` characters are eaten.** A `%` in `execute_python` code hits a printf-style formatter in the log path and mangles the statement (`'%s:%d'` arrives as `':1'`). Use f-strings or concatenation, never `%` formatting.

**`execute_python` takes ONE line.** The bridge splits the command on whitespace and rejoins with single spaces, so runs of spaces collapse — indentation-sensitive multi-line code will not survive. For multi-line code use `execute_python_script` (it sends the script through the `bridge.execute_python.b64` verb); otherwise use single-line comprehensions.

**Write big results to a file, not through the return value.** The log is echoed twice, so large output doubles. `open('C:/path/x.json','w').write(...)` from `execute_python`, then read the file.

**Terrain specifics** (each cost an hour to find):

- `CHeightmap::GenerateTerrain` always calls `Normalize()` and resets max height to `terrainSize/4 + waterLevel`. Height is therefore **not** controllable via its parameters, and `iCover`/`iSharpness` are accepted and then never used. To change height use `terrain.reduce_range_heavy()` (`LowerRange(0.8)`, scales relief around the water line) — non-interactive.
- `terrain.flood_layer` has **two silent-failure paths**: it returns with no warning if `CheckSectorPalette` fails, and its painter silently no-ops if `GetTerrainTextureNodeSizeMeters()` is 0. It reports success either way. Use `bridge.terrain.generate_surface_texture` instead.
- Terrain layer **selection does not survive a level reload**.
- A layer texture must be power-of-two, and the layer's texture is packed R-in-low-byte while an RGB layer tile is `(R<<16)|(G<<8)|B` — R and B swap when crossing between them.

**Deploying a rebuilt plugin:**

- The installed DLL is **locked while Sandbox runs**; close Sandbox, copy the DLL into `<engine>\bin\win_x64\EditorPlugins\`, then relaunch. Plugins load once at startup — restarting the MCP connector does nothing for C++ changes.
- **Verify the built DLL actually contains your change** before deploying: search its bytes for the new verb name, for example with PowerShell `Select-String -Path ClaudeBridgePlugin.dll -Pattern 'bridge.myverb' -Encoding ascii`. A build that compiled unchanged source is a known trap.

## Non-interactive terrain shaping

Confirmed by reading `TerrainDialog.cpp` — these apply a fixed factor with no dialog, so they are safe to script:

| Call | Effect |
|---|---|
| `terrain.reduce_range_heavy()` | `LowerRange(0.8)` — flattens relief around the water level, keeps the shoreline |
| `terrain.reduce_range_light()` | `LowerRange(0.95)` |
| `terrain.flatten_heavy()` | `Flatten(0.5)` — scales around 0, sinks terrain relative to water |
| `terrain.flatten_light()` | `Flatten(0.75)` |
| `terrain.smooth()` / `terrain.smooth_slope()` / `terrain.smooth_beach_coast()` | smoothing passes |
| `terrain.make_isle()` / `terrain.normalize()` / `terrain.invert_heightmap()` | whole-map reshaping |

## Plugin verbs (`bridge.*`)

The most common ones, implemented in `plugin/ClaudeBridgePlugin/ClaudeBridgePlugin.cpp` for things no registry exposes. Call via `run_console_command`. The plugin has many more (`bridge.window.*`, `bridge.dialog.*`, `bridge.input.*`, `bridge.file.*`, `bridge.object.*`, `bridge.vegetation.*`, `bridge.db.*` and others); the full list is in [plugin-protocol.md](plugin-protocol.md) and the source.

| Verb | Purpose |
|---|---|
| `bridge.terrain.info` | Heightmap size, real min/max/avg elevation, sector layout, RGB-layer state, `terrainTextureNodeSizeMeters`. Use this to judge terrain **numerically** instead of by eye. |
| `bridge.terrain.list_layers` | Every layer: index, id, name, selected, inUse, hasTexture, material, altitude/slope rules |
| `bridge.terrain.select_layer <i\|name>` | The only way to reselect an existing layer |
| `bridge.terrain.delete_layer <i\|name>` | Select + remove |
| `bridge.terrain.set_layer_params <layer> <altStart> <altEnd> <slopeMin> <slopeMax>` | Altitude (m) and slope (deg) rules driving the blend |
| `bridge.terrain.set_layer_texture <path>` | `CLayer::LoadTexture` on the selected layer (definition only — paints nothing) |
| `bridge.terrain.generate_height [passes] [freq] [freqStep] [fade] [cover] [seed] [sharp] [smooth]` | Fractal generation (but see the Normalize gotcha) |
| `bridge.terrain.generate_surface_texture [repeat] [altFeather] [slopeFeather]` | **Bakes layers into the visible base texture.** First textured layer = unmasked base; later layers blend by slope/altitude. Save + reload to see it. |
| `bridge.cvar_get` / `bridge.cvar_set` | Typed CVar access |
| `bridge.entities.list` / `bridge.entities.teleport` | Entity listing and movement |
| `bridge.execute_command` / `bridge.execute_python` | Registry escape hatches |

After any terrain change: `general.save_level` then `load_level(...)`. The engine reads the baked texture from `terraintexture.pak` at load time, so changes are not visible until a reload.

**Verifying terrain visually without a screenshot:** `terraintexture.pak` is a plain ZIP of `tileX_Y.raw` files, each an 8-byte header (width, height as uint32) followed by raw pixels in **BGR** byte order. Copy it out, reassemble the tiles into a mosaic, and you get a top-down view of the baked terrain; this was used for verification because `IRenderer::ScreenShot` returns false in edit mode and `general.take_screenshot()` produces no file.
