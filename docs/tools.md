# Tool reference

Generated by `tools/gen_tools_doc.py` from `server.py`. Do not edit by hand; edit the docstrings in `server.py` or `tools/tool_meta.json` and run the generator again.

This server targets CRYENGINE 5.7.1. Tool names, signatures and the first paragraph of each description are read from `server.py` with `ast`. The flag columns, the side-effect text and the helper modules come from a source review recorded in `tools/tool_meta.json`; they were not produced by running the tools. Where the review did not read a helper module, the entry says "not verified".

## How to read the tables

Each family section has two parts: a table of flags and side effects, then a list of signatures with the description from the tool's docstring (its first paragraph). At run time, `tool_guide` returns the same kind of map from the registered tools; its grouping differs from the one used here.

| Column | Meaning |
|---|---|
| Needs editor | Whether the tool talks to a running Sandbox editor through the bridge plugin (TCP port 37778). `yes`: it fails or returns an error without one. `no`: it works without an editor. `optional`: it works offline under a condition given in the side-effects text or the description (for example an `asset_dir` argument, a `refresh` flag, or a mode that only probes). `cache`: it answers from a saved dump; only a first run or a refresh asks the editor. |
| Writes files | `yes`: it writes files under the project, the server's data folders or the engine's output folders (pictures, caches, level files, logs). `conditional`: only with a certain argument (for example `apply=true`, `persist=true`, `accept_baseline`). `cache`: it only writes its own cache file. `no`: it reads, or changes editor state in memory only. `not verified`: the review did not read the code that would decide it. |
| Closes editor | `yes`: the tool closes Sandbox.exe to run, as a graceful save-and-close (it refuses unless `allow_editor_close=true` is passed). `depends on kind`: `start_job` closes the editor only for some job kinds, see below. `no`: it does not close the editor. |
| Launches game | `yes`: the tool starts the packaged game executable. `depends on kind`: see `start_job`. `no`: it does not. |
| Side effects | Condensed from the review. "Unsaved" means the change is in the editor's memory until the level is saved. |
| Helpers | The Python modules (and a few functions) in this repository that do the work. See [modules.md](modules.md). |

`wait_for_editor`, `health_check` and `project_info` are probes: they report the state of the editor or the project and change nothing (`wait_for_editor` only starts Sandbox when `CLAUDE_AUTO_RECOVER=1`, which is off by default).

Editor changes are not file writes: a tool marked `Writes files: no` and `Needs editor: yes` can still change the open level in memory (see its side-effects text), and a graceful editor close can save such changes.

### Prerequisites per tool

Some tools need something that is not part of this repository. The prerequisite is named in the tool's description; the common ones are:

- A saved offline copy of the CRYENGINE manual (`search_manual`, `read_manual_page`, `manual_toc`): not shipped; set `CRYENGINE_DOCS`, see `catalogs/scrape_cryengine_docs.py`.
- The CRYENGINE engine source tree, via the environment variable `CRYENGINE_SOURCE` (some catalogs and checkers).
- The GameSDK sample installed with the engine (`gamesdk_audio`, `study_gamedata` and similar).
- External programs for the audio tools (Piper for voices, ffmpeg for conversion) and, for the animation scripts, a local MotionBricks or Kimodo install.

`docs/installation.md` lists the setup steps. A tool whose family or description names the Ashvale example (`preview_voice`, `render_voices`, `make_music`, `visual_check` and the tools built on the Ashvale shot lists) is tied to that example project and is not a general tool.

### Catalogs captured from the editor

The catalog tools answer from dumps in `engine_data/`. Most dumps are captured once from a running editor and are not all shipped: `schematyc_env.json`, `uqs_catalog.json` and `editor_api_samples.json` are not in a fresh clone. A tool whose dump is missing has nothing to answer from until the matching capture command (named in its description, for example `python catalogs/schematyc_catalog.py --capture`) has been run once with the editor open. Such tools are marked `cache` in the Needs editor column.

## Project and server

Server and project state, the editor probe, the saved-output pager and the tool map.

| Tool | Needs editor | Writes files | Closes editor | Launches game | Side effects | Helpers |
|---|---|---|---|---|---|---|
| `project_info` | optional | no | no | no | reads only; editor: queried if reachable; the file-side answer works without it | project_root, bridge_py |
| `use_project` | no | yes | no | no | writes or deletes active_project.txt (next to project_root.py) | project_root |
| `ping` | yes | no | no | no | none | get_cvar |
| `health_check` | no | no | no | no | reads only; editor: probes for it; works without | health |
| `server_info` | no | no | no | no | reads only | server_support |
| `read_output` | no | no | no | no | reads only | server_support |
| `tool_guide` | no | no | no | no | none | FAMILIES, FastMCP internals |

- `project_info() -> dict`
  WHICH PROJECT these tools work on, and which one the open editor runs. The tools (asset checks, lints, jobs, package, snapshots, catalogs ...) read and write the ACTIVE project's folder; the EDITOR-side tools talk to whatever project the open Sandbox has loaded. They are two settings: this tells both, and says when they disagree (then editor-side results describe a different project than the files). The active project is chosen by the environment variable CRYENGINE_PROJECT, else active_project.txt in the repository root, else the parent folder of the repository (the layout where the repository sits inside the project folder; see bridge/project_root.py). Change it with use_project. Also lists the projects the engine knows (projects.json).
- `use_project(path: str) -> dict`
  Make another CRYENGINE project the one these tools work on (a folder holding Game.cryproject, or the file itself). Writes active_project.txt in the repository root; the tool modules read it when the MCP server starts, so RESTART/RECONNECT the cryengine MCP server afterwards (the result says so). Nothing in the project is changed and the editor is not touched: the editor-side tools keep describing whatever project the open Sandbox has until the editor is reopened on this one (the engine's project list is projects.json). path='' clears it (back to the parent folder of the repository).
- `ping() -> dict`
  Connectivity check -- confirms the bridge is reachable and the engine is actually ticking it (i.e. you're in an active Play session), without changing any state. Reads the r_DisplayInfo cvar, which exists in every CRYENGINE project.
- `health_check() -> dict`
  Can the working state be trusted right now? One report: is the editor up and its bridge answering with a level loaded, is each PACKAGED build older than the project's code and assets (shoot_game and the tests show the package, not the project), is the shader cache older than a material, is the watchdog scheduled, is a stray lock blocking it, what jobs are running, how much disk is free. Reads only, about a second. Each item is ok | info | warn | fail with a fix. Run it before believing a picture or a test, and after anything odd (nothing visible changed? the package may be stale).
- `server_info() -> dict`
  About THIS running MCP server: when it started, its pid, and which of its modules were EDITED after it started (the running server keeps the old code until the MCP connector is restarted: `restart_note` says "restart the MCP connector to load: ..." with the files). Also: whether auto-recovery is on, whether the editor was closed on purpose (marker file), how many times this server brought the editor back, the state of the catalog dumps (stamped against the installed plugin build), and how many saved tool outputs exist. Reads only.
- `read_output(id: str, key: str = '', offset: int = 0, limit: int = 50) -> dict`
  Page through a tool result that was too big to return (over ~20,000 characters): the tool answered with `output_truncated`, an `output_id` and the saved file. key: a path into the saved result ('items', 'items.3', 'rows.0.name'; empty = the top level). A list is paged by items, a dict by keys, a text by lines: offset and limit select the page; `next_offset` says where the next page starts (null at the end). A single item that is itself too large comes back described: give a deeper key. Files are in job_runs/out/.
- `tool_guide(family: str = '') -> dict`
  The map of every tool in this server, by family, each with the first sentence of its description. family: part of a family name to show only that one ('verify', 'jobs', 'make', 'objects', 'terrain', 'navigation', 'editor', 'study', 'start'). Built from the registered tools themselves; a tool no family claims is listed under 'unclassified'.

## Editor and bridge control

Raw access to the running Sandbox editor through the bridge plugin: console, commands, Python, windows, dialogs, undo, notifications.

| Tool | Needs editor | Writes files | Closes editor | Launches game | Side effects | Helpers |

| `execute_editor_command` | yes | no | no | no | Arbitrary editor mutation; deny-list for general.exit etc. | server_support (editor_api.denied) |
| `execute_python` | yes | no | no | no | Arbitrary; regex deny-list | server_support |
| `goto_position` | yes | no | no | no | Camera only | run_console_command |
| `get_cvar` | yes | no | no | no | reads only | bridge |
| `set_cvar` | yes | no | no | no | Changes live engine state | bridge |
| `execute_python_script` | yes | no | no | no | Arbitrary; same deny-list | server_support |
| `list_windows` | yes | no | no | no | reads only | bridge |
| `list_dialogs` | yes | no | no | no | reads only | bridge |
| `click_dialog_button` | yes | no | no | no | Real click: can discard or confirm | bridge |
| `wait_for_editor` | no | no | no | no | only probes; with CLAUDE_AUTO_RECOVER=1 (off by default) it may start Sandbox.exe and replace a crashed one with taskkill /F via bridge_watchdog.recover | bridge_py, bridge_watchdog, health |
| `editor_notify` | yes | no | no | no | shows a notification | editor_ux |
| `editor_undo` | yes | no | no | no | undo/redo changes the open level | editor_ux |

- `run_console_command(command: str, really: bool = False) -> str`
  Execute an arbitrary CryEngine CONSOLE command (CVars and true console commands only -- see execute_editor_command/execute_python for Sandbox's other two command registries) and return whatever it logged.
- `execute_editor_command(command: str, really: bool = False) -> dict`
  Execute a Sandbox ICommandManager command -- the "module.command" namespace registered via REGISTER_EDITOR_AND_SCRIPT_COMMAND / REGISTER_PYTHON_COMMAND (asset.*, level.*, general.save_level, etc). This is a DIFFERENT registry from run_console_command's IConsole and execute_python's Python interpreter -- if a command isn't found here, try execute_python instead (many general.* object/entity commands, e.g. general.new_object, are Python-interpreter-only and never reach this registry at all).
- `execute_python(code: str, really: bool = False) -> dict`
  Execute a line of Python through Sandbox's actual Python interpreter (the same one the in-editor Python console uses). Reaches commands registered via REGISTER_ONLY_PYTHON_COMMAND_WITH_EXAMPLE that execute_editor_command's ICommandManager path can never see -- notably general.new_object and general.create_object, the standard way to spawn objects/entities from script. Modules are pre-imported as "from sandbox import <module>", so call the bare module name.
- `goto_position(x: float, y: float, z: float, ax: float = 0, ay: float = 0, az: float = 0) -> str`
  Move the editor camera / player to a world position, with optional angles in degrees (equivalent to the console's `goto` command).
- `get_cvar(name: str) -> dict`
  Read a console variable's current value and help text directly from the engine (via ICVar), e.g. get_cvar("r_DisplayInfo") or get_cvar("e_TimeOfDay"). More reliable than run_console_command for reading values, since it doesn't depend on scraping console text.
- `set_cvar(name: str, value: str) -> dict`
  Set a console variable to a new value directly via ICVar, e.g. set_cvar("r_DisplayInfo", "1") or set_cvar("e_TimeOfDay", "12"). Returns the cvar's value after the change, read back from the engine.
- `execute_python_script(code: str, include_engine_log: bool = False, really: bool = False) -> dict`
  Run a MULTI-LINE Python script inside Sandbox with indentation intact (bridge.execute_python.b64). Prefer this over execute_python for anything with a loop, try/except or def -- execute_python collapses whitespace.
- `list_windows() -> dict`
  List Sandbox's top-level windows (out-of-band: answers even while a modal dialog blocks the main thread). The only way to notice that a command is stuck on a dialog such as "MNM Navigation Rebuilding request" or "Navigation System Warning".
- `list_dialogs() -> dict`
  The editor's open dialogs, read through Qt on the GUI thread (bridge.dialog.list): title, question text, and buttons {text, standard, enabled, default}. Answers even while a queued command is stuck inside the dialog -- it has its own queue.
- `click_dialog_button(button: str, title: str = '') -> dict`
  Click a dialog button by name (bridge.dialog.click): yes / no / ok / cancel / save / discard / default, or the button's text without spaces. Targets the active modal unless `title` (part of one) picks another. Needs no focus and cannot reach another program's window. It is a real click, so the dialog's caller gets that button as its answer; confirm with list_dialogs.
- `wait_for_editor(timeout: int = 240, require_level: bool = True) -> dict`
  Wait until the editor is back: Sandbox's bridge answers and (by default) the level is loaded. Use it after a job that closed the editor (package, tests, shader_cache, shoot, visual, cvar_probe): the watchdog reopens it within 5 minutes, the level loads in ~15 s. With CLAUDE_AUTO_RECOVER=1 (off by default) this call itself may start Sandbox.exe (and replace a crashed one, taskkill /F) via bridge_watchdog.recover. Returns at once when it is already up. On a timeout it says why: what the watchdog last did, whether Sandbox.exe exists, whether a lock holds the watchdog off, what jobs run. timeout is 1 to 900 seconds; require_level=false returns as soon as the bridge answers.
- `editor_notify(title: str, message: str = '', level: str = 'info') -> dict`
  Tell the user something INSIDE the open editor: a non-modal message in the Notification Center (INotificationCenter::ShowInfo / ShowWarning / ShowCritical, the manual's preferred way: no dialog, no focus change). level: info | warning | critical. title up to 80 characters, message up to 400. Use it when a long job ends or a check finds something while the user is looking at the editor, not instead of answering in the conversation. Returns the notification's id (it cannot read back whether the user saw it).
- `editor_undo(action: str = 'info', steps: int = 1, expect: str = '') -> dict`
  The editor's own UNDO stack (IUndoManager; what Ctrl+Z / Ctrl+Y use). action 'info': mode, undo/redo step counts and the last 10 undo step names, newest first. 'undo': takes back the newest `steps` steps, but ONLY if every one of them contains `expect` in its name (the stack also holds the user's own edits: an undo of the wrong step is refused, nothing is changed). 'redo': re-applies what an undo took back. Steps recorded by the tools: place_object ('Create new object (name)', by the editor's own Python function), create_object ('Claude: create <Type> (name)'), object_properties ('Claude: set properties'). The bridge's other object verbs (used by the test tools' scratch objects) record nothing unless asked. Does not save the level.
- `editor_panel(action: str = 'status') -> dict`
  A "Claude Status" PANE inside the Sandbox editor, written in Python/PySide2 and run by the editor's own interpreter (no C++, no file added to the engine folder): the open level and its object count, the bridge plugin file, the last accepted project-audit baseline, the last editor-suite run and the newest jobs, refreshed every 3 seconds. action 'status' says whether the pane class is registered and how many panels are open; 'open' registers the class once per editor session (SandboxBridge.register_window; the registration is lost when the editor restarts) and opens the pane as a floating window in the user's editor: do it when the user wants to watch, not unasked; 'close' closes that window and nothing else. The pane only reads small files and cheap editor calls: it never calls the bridge socket or starts a process (a blocking call from inside the editor's Python deadlocks the editor). Sandbox auto-loads Python plugins only from the ENGINE install (Editor/Python/plugins/*/startup.py), which this does not touch.

- `load_level(level_name: str, save_current: bool = True) -> dict`
  Load a level by name via Sandbox's asset system (asset.edit), the supported way to open a level from outside the editor UI -- console's `map <level>` is unconditionally refused while running inside the editor (CCryAction::MapCmd's gEnv->IsEditor() guard). The level that is open is SAVED first (save_current=True): leaving a modified level opens a modal 'Save Level?' prompt that blocks the bridge. If that save FAILS the level is not left (the answer says save_failed); save_current=False skips the save and discards unsaved changes. It WAITS until the level is the open one (up to 3 minutes) and returns {ok, level, seconds, n_warnings, ...} (n_warnings = warning lines the load logged); an open dialog is reported with `dialog_open` and what to click, never waited out. A level that does not exist is refused with the list of the ones that do.
- `list_entities(name_filter: str = '', limit: int = 100, offset: int = 0) -> dict`
  List entities currently in the loaded level: {"items": [{"id", "name", "pos": [x, y, z]}], shown, offset, total, total_is_lower_bound, truncated, next_offset, note}. Pass name_filter to only return entities whose name contains that substring. The bridge returns at most 200 entities (truncated=true says when that cut the list: narrow the filter); limit (1-500, default 100) and offset page what it returned.
- `teleport_entity(name: str, x: float, y: float, z: float) -> dict`
  Move an entity (found by exact name, via IEntitySystem::FindEntityByName) to a new world position. Unlike goto_position, this moves a specific named entity rather than the camera/player.
- `list_objects(name_filter: str = '', limit: int = 100, offset: int = 0) -> dict`
  List EDITOR objects (brushes, entities, archetypes, nav areas, shapes...) as {"items": [...], shown, offset, total, total_is_lower_bound, truncated, next_offset, note}: each item has name, type, pos, rotDeg, scale, material, hidden/frozen. The bridge returns at most 500 (truncated=true says when that cut the list; total is the level's real object count when no filter is given); limit (1-500, default 100) and offset page what it returned. Pass name_filter (case-insensitive substring) on big levels. Unlike list_entities this includes non-entity objects such as NavigationArea. For a complete, uncapped view of a level use inspect_level instead. (object.get_all_objects is broken under Sandbox's Python 3: it raises "expected bytes, str found".)
- `list_archetypes(library: str = 'Characters', name_filter: str = '') -> list`
  List entity archetypes in Libs/EntityArchetypes/<library>.xml (read straight from the loose file or the .pak) of the loaded project and then of the GameSDK sample, with the fields that define an AI character: faction, behavior_tree, equipment, navigation_type, model. GameSDK libraries: Characters, Animals, Lights, Props_Destroyable, Props_Interactive, Props_Physics. An unknown library is refused with the list of the ones that exist.
- `spawn_archetype(archetype: str, x: float, y: float, z: float, name: str = '') -> dict`
  Place an entity archetype -- the way GameSDK places its AI soldiers (airfield's Multiplayer_AI layer: 12 x Characters.Enemy.Easy_Rifle). `archetype` is "Library.Name" (e.g. "Characters.Enemy.Easy_Rifle") or a GUID. The archetype carries faction, behavior tree, equipment, model and nav agent type, so nothing else needs setting. The AI only moves if it stands on a navmesh built for its esNavigationType -- see create_navigation_area. Archetype properties are NOT readable per instance through general.get_entity_property ("invalid property"); read them with list_archetypes.
- `create_navigation_area(points: list, floor_z: float, height: float = 16.0, exclusion: bool = False, name: str = '', remove_inaccessible_triangles: bool = True) -> dict`
  Create an MNM NavigationArea from WORLD-space [x, y] polygon points.
- `create_ai_path(points: list, name: str = '', agent_type: str = 'Villager', closed: bool = False, allow_off_navmesh: bool = False) -> dict`
  Create an AIPath shape from WORLD-space [x, y, z] points -- the editor's "AI Path" object, a named route designers draw for AI to walk.
- `create_nav_seed_point(x: float, y: float, z: float, name: str = '') -> dict`
  Place a NavigationSeedPoint. Navmesh triangles connected to a seed point are kept; islands with no seed (rooftops, inside rocks) are removed when the area has RemoveInaccessibleTriangles on. Put one on walkable ground inside every separately reachable region. Woodland has 5 for its 5 inclusion areas.
- `regenerate_navigation(agent_type_index: int = 0) -> dict`
  Rebuild the navmesh for one agent type WITHOUT the modal dialog, via ai.regenerate_agent_type_layer<N> (RequestGlobalUpdateForAgentType). N is the agent type's order in Scripts/AI/Navigation.xml (GameSDK: 0 = MediumSizedCharacters, 1 = VehicleMedium). Do NOT use ai.regenerate_agent_type_all or ai.regenerate_mnm_type('all'): both open "MNM Navigation Rebuilding request" and block the editor until clicked. The rebuild runs in the background; watch it with set_ai_debug(navigation=1).
- `set_ai_debug(navigation: int = 1, movement: bool = False, path_follower: bool = False, pathfinding: bool = False, off: bool = False) -> dict`
  Toggle the AI debug overlays that make navigation visible in the viewport. navigation: 0 off, 1 triangles+contour, 2 +mesh, 3 +external links, 5 island IDs (islands = regions not connected to each other). movement shows each actor's plan ([FollowPath] ...); path_follower draws the followed path. ai_DebugDraw is the master switch and is set automatically.
- `export_level(wait_seconds: float = 120.0, answer_dialogs: bool = True, max_attempts: int = 3) -> dict`
  File > Export to Engine (exporter.export_to_engine). This is what writes the navmesh (mnmnav<mission>.bai), cover surfaces (cover<mission>.bai) and level.pak, so AI navigation survives an editor restart and works in the launcher. general.save_level alone does NOT write the navmesh.
- `create_collision_wall(x: float, y: float, z: float, length: float, height: float, thickness: float = 0.5, yaw_deg: float = 0.0, name: str = '', material: str = 'materials/special/collision_proxy') -> dict`
  Place an invisible wall that blocks the player/vehicles - GameSDK woodland's border technique (layer Player_Collisions: 147 meshes with materials/special/collision_proxy_entitiesonly).
- `get_entity_physics(name: str) -> dict`
  Live physical state of one entity (needs the ClaudeBridge plugin build with bridge.entities.physics). For a character (PE_LIVING) it returns the collider (sizeCollider, heightCollider, capsule, colliderBottom/Top, stepUpHeight), dynamics (kInertia, kInertiaAccel, kAirControl, gravity, mass, slide/climb/jump/fall angles in DEGREES, maxVelGround, bActive), and the live contact state (bFlying, vel, velRequested, groundSlope, groundHeight, bStuck, bSquashed), plus collision class type/ignore bits and parts. Works in edit mode; the player only has meaningful living state in game mode (game.toggle_game_mode). GameSDK's player entity is named "Dude" in the editor.
- `component_properties(entity: str, component: str, values: dict = None, persist: bool = False) -> dict`
  Read, and optionally set, the properties of one component on an entity -- the values the Inspector shows under a component (needs the ClaudeBridge plugin build with bridge.component.properties).
- `place_object(kind: str, asset: str, name: str, position: list[float], rotation_deg: list[float] | None = None, scale: list[float] | None = None, material: str = '', overwrite: bool = False) -> dict`
  Place one object in the OPEN editor's level, checked before and read back after. kind 'brush': asset is a mesh path ('objects/props/.../x.cgf' or '%ENGINE%/EngineAssets/Objects/primitive_cube.cgf'; it must exist, loose or in a pak); kind 'entity': asset is an entity class name. name: letters, digits, _ (starting with a letter). position [x,y,z] metres (z is the object's origin: a brush's pivot is not always its base: cgf_bounds says where a mesh really is). rotation_deg [rx,ry,rz], scale [sx,sy,sz], material a game path. An existing name is refused unless overwrite=true. Returns the object as the editor reports it and any difference from what was asked. The level is NOT saved (save with execute_editor_command general.save_level when the phase is done). Needs Sandbox open with the level: health_check says.
- `delete_objects(names: list[str] | None = None, prefix: str = '', really: int | None = None) -> dict`
  Delete level objects, safely. Give exactly one of names (a list of exact names) or prefix (at least 3 characters: every object whose name STARTS with it). It is a DRY RUN until `really` equals the number of objects that match: the first call lists what would go and how many, the second passes that number. A different number deletes nothing. More than ~490 matches (the editor's list is capped near 500) is refused: narrow the prefix. The level is not saved. Needs Sandbox open with the level.
- `object_types(text: str = '') -> dict`
  The kinds of object the editor can create (the engine's own list, 36 in this build): AI (AIPath, AIShape, NavigationArea, CoverSurface...), Area (AreaBox, AreaSphere, Shape, VisArea, Portal, OccluderArea, WaterVolume, ClipVolume...), Audio, Brush, Components (EntityWithComponent), Designer, Misc (Camera, Comment, Decal, DistanceCloud, EnvironmentProbe, River, Road, Rope, SplineDistributor, ReferencePicture), Static Mesh Entity... Create one with create_object. Needs Sandbox open. With `text`: the saved CATALOG of what the engine gives a fresh object of each type (every property with its default and the child nodes: engine_data/object_catalog.json, made by creating and deleting one scratch object of each type), searched by words in the type, the category or a property name ('fog', 'height', 'sound'): works with the editor closed.
- `create_object(type: str, name: str, position: list[float]) -> dict`
  Create an editor object of ANY engine type (see object_types: River, Road, Rope, WaterVolume, Decal, AreaBox, VisArea, Portal, OccluderArea, EnvironmentProbe, SplineDistributor, ...) at a world position. Refuses an unknown type, a bad or taken name. Returns the object's properties as the engine's own serializer reports them (every property a layer file would hold). The level is NOT saved: BUT a graceful editor close (a job, a plugin deploy) saves it, so delete what you create for an experiment (delete_objects) before anything restarts the editor. Splines (Road, River) start with no points: spline_points sets them; object_properties sets the rest. Brushes and entities with a mesh or a class: place_object. The creation is one editor UNDO step ("Claude: create <Type> (<name>)"): Ctrl+Z removes it (editor_undo). VIS AREAS: the 3D engine classifies an area by a word in its name, so a VisArea must be named with 'visarea' in it (and not 'portal'), or it silently does nothing; the answer carries `warnings` when the name you gave will not work (see visarea_check).
- `object_properties(name: str, set: dict[str, str] | None = None) -> dict`
  Read, and optionally set, every property of one editor object, through the engine's own serializer (the same XML a layer file holds): a River's Width, StepSize, VolumeDepth, Fog*, Caustics*; a Road's Width, TileLength, SortPriority, EraseVegWidth; a Rope's `Rope/mass`, `Rope/radius`, `Rope/num_seg`; a Decal's ProjectionType, SortPriority; a WaterVolume's depth and fog; plus Pos, Rotate, Scale, Material, MinSpec, ViewDistRatio. `set`: {key: value}; a key is an attribute of the object, or 'Child/key' for an attribute of a child node. The change is one undo step and is read back: `not_applied` lists every key the object did not end up holding (a misspelt key is reported, not ignored). Type, Id, Layer and LayerGUID cannot be set. Not saved.
- `spline_points(name: str, points: list[list[float]], widths: list[float | None] | None = None) -> dict`
  Set the points of a spline or shape object from WORLD positions [[x,y,z], ...]. SPLINES (Road, River, SplineDistributor, WaterWave ...; at least 2 points) are stored the way the editor stores them (local to the object, with the editor's own Bezier smoothing, so the curve is what clicking the same points would give); widths: optional per-point widths (null = the default width of the object). SHAPES (WaterVolume, Shape, VisArea, Portal, OccluderArea, AIShape, AIPath, NavigationArea; at least 3 points) are a plain polygon: the editor RE-CENTRES the object on the minimum corner of its points (measured: the object's position moves, the world points stay as asked); the answer gives the new position and the world points it now holds. A river, road or water volume lies at z: one at the terrain's height is hidden inside it. Returns the number of points the object holds afterwards. Not saved.
- `add_component(entity: str, component: str, values: dict = None) -> dict`
  Add a component to a LEVEL entity the way the Inspector's 'Add Component' does (needs the editor): `component` is a class name, GUID or label from the Schematyc environment (schematyc_search lists them: "Particle Emitter", "Projector Light", "SensorVolume", "Cloth", "Decal", "Rigidbody", "Point Constraint" ...). `values` (optional) is a (possibly nested) dict of the component's members, applied after the add through component_properties (the complete property set is merged in). The answer holds the new instance's GUID, the properties the component now has, and `not_applied`: every requested value the component did not end up holding. There is no undo step for an add; the level is flagged modified (save_level to keep it). Check the result with entity_check (N002-N004) and component_properties. A singleton the entity already has is refused by the engine.
- `link_area_target(area: str, entities: list[str], replace: bool = False) -> dict`
  Link entities as the TARGETS of an area object (AreaBox, AreaSphere, AreaShape/Shape): the entities then receive the engine's enter/leave/fade area events when something carrying ENTITY_FLAG_TRIGGER_AREAS (the player, through its audio listener) crosses the area; an AreaTrigger entity turns them into flow outputs. This is the Inspector's link between an area and its entities (the `<Entities><Entity Id=..>` child of the area object). The Python `general.add_entity_link` is a DIFFERENT link type. `replace=false` keeps the targets the area already has. The answer lists the Ids the area holds afterwards and `not_applied`: names that are no entity or that the area did not keep. Not saved.
- `flow_graph_add(entity: str, nodes: list[dict], edges: list[dict], description: str = '', group: str = '', dry_run: bool = False) -> dict`
  Put a flow graph INTO THE LEVEL: store it as the `<FlowGraph>` child of a FlowgraphEntity object (place_object kind='entity' asset='FlowgraphEntity' first), the way the editor does (the GameSDK sample's gameplay layers). Before anything is written the same nodes and edges are loaded by the engine's own loader as a throw-away standalone file (flow_check F001-F008: unknown node class, a port the node does not have, an input the engine did not keep) and the level is only touched if that finds no error (dry_run=true: check only). nodes: [{"id": "1", "class": "entity:AreaTrigger", "entity": "zone_trig" (entity NAME, resolved to its GUID; for nodes that target an entity), "inputs": {"Enable": "1"}, "pos": [x, y]}]; edges: [{"from": "1.Enter", "to": "2.input"}] ("<node id>.<port>"). flow_nodes lists node classes and ports. The answer says what the engine check found and the node/edge counts read back from the object (`stored` is true only when they match). Not saved (save_level); whether the graph RUNS needs the game or editor game mode.
- `save_level() -> dict`
  Save the level the editor has open (the editor's own general.save_level): terrain, layers, vegetation, objects. Does NOT write the navmesh or level.pak: export_level does. Answers {saved, level, objects}.

- `generate_terrain_height(passes: int = 4, frequency: float = 3.0, frequency_step: float = 1.7, fade: float = 0.8, cover: int = 128, seed: int = 17, sharpness: float = 0.995, smoothness: int = 1) -> dict`
  Replace the current (flat) heightmap with real fractal-noise height variation -- the same generator as Sandbox's "Generate Terrain" dialog (CHeightmap::GenerateTerrain). All args are optional; defaults are a moderate, natural-looking setting. Valid ranges: passes 1-10, frequency 1.1-10.0, frequency_step 1.0-2.5, fade 0.1-2.0, cover 0-255, seed 0-32, sharpness 0.990-0.999, smoothness(blur) 0-3. Width/height are taken from the heightmap's own current resolution. This REPLACES the heightmap of the open level (nothing is saved until save_level; snapshot_project first, editor_undo can revert it); values outside the ranges are refused.
- `set_terrain_layer_texture(path: str) -> dict`
  Point the currently-selected terrain layer at a custom diffuse texture (CLayer::LoadTexture), replacing the default white.dds. Path is resolved through CryPak relative to the project's Assets folder (e.g. "textures/terrain_grass_dirt.bmp"). Must be power-of-2 sized. Requires a terrain layer to already be selected (e.g. via terrain.create_layer).
- `list_terrain_layers() -> list`
  List every terrain layer as {"index", "id", "name", "selected"}. "selected" reflects CLayer::IsSelected() -- what set_terrain_layer_texture and the ICommandManager terrain.flood_layer/terrain.delete_layer/ terrain.duplicate_layer/terrain.move_layer_* commands actually operate on. Selection does not survive a level reload, so check this before assuming a prior select_terrain_layer call (or terrain.create_layer, which auto-selects) is still in effect.
- `select_terrain_layer(layer: str) -> dict`
  Select a terrain layer by 0-based index or by exact name (first match), via CTerrainManager::SelectLayer -- the only way to (re)select an EXISTING layer, since terrain.create_layer only auto-selects the layer it just created. Needed before set_terrain_layer_texture or any of the "operates on the selected layer" ICommandManager commands (terrain.flood_layer, terrain.delete_layer, terrain.duplicate_layer, terrain.move_layer_*) when the layer you want isn't the one already selected. Pass an int-like string ("0", "2", ...) or a layer name.
- `terrain_hole(x: float, y: float, width: float, height: float, make: bool = True) -> dict`
  Make (make=true) or fill (false) a rectangular HOLE in the open level's terrain, in world metres (x, y = the corner with the smaller coordinates): a cellar, a cave mouth, a well shaft, a place where a mesh replaces the ground. The editor's own call (CHeightmap::MakeHole) through the ClaudeBridge plugin; before this only the mouse brush could. The answer is read back (`as_asked`, holes counted in the rectangle, `centre_is_hole`). Holes are saved with the level and exported to terrain.dat. Not saved: save_level, then export_level. In the packaged game the ground has no collision there (probe: claude_ground x y). Needs the plugin build that contains bridge.terrain.hole (rebuild and deploy the plugin, see docs/installation.md).
- `new_level(name: str, resolution: int = 1024, unit_size: float = 1.0, terrain: bool = True) -> dict`
  Create a NEW level and open it in the editor (the editor's own general.create_level; 0.6 s): flat terrain at 32 m, water at 16 m, no objects. The level that is open is SAVED first (leaving a modified level opens a blocking 'Save Level?' prompt). Nothing is overwritten: an existing name is refused. name: a letter, then letters/digits/_ (40 at most); resolution: samples per side, 128 to 4096; unit_size: metres per sample (0.25 to 16), so the terrain is resolution x unit_size metres square (1024 at 1.0 = 1 km). The new terrain draws BLACK until its colour texture is baked: terrain_shape, terrain_layers(action='bake'). Next steps for a game level: terrain_shape -> terrain_layers (add layers, bake) -> vegetation -> place_object / create_object with z from terrain_height -> level_validate / level_check -> save_level -> export_level.
- `terrain_shape(style: str = 'hills', seed: int = 1, base_height: float | None = None, max_height: float | None = None, flat_zones: list[dict] | None = None, erosion: int = 0, preview: bool = False, restore: str = '') -> dict`
  Shape the OPEN level's terrain from a style, without the game: style flat | hills | mountains | island; seed picks the variation; base_height / max_height are the lowest and highest ground in metres (default: a few metres over the water, and a range that scales with the terrain's size so a small map is not a cliff); flat_zones = [{"x", "y", "radius", "blend", "height"}] in WORLD METRES cuts level platforms for buildings (height defaults to the ground's mean there; blend defaults to radius/2); erosion = droplets for drainage valleys (0 = none; ~250 per 1,000 samples is visible). preview=True reports the numbers (min/max, share steeper than 30 degrees, each zone's real height and spread) and changes nothing. The old ground is BACKED UP first (engine_data/terrain_backups): pass restore=<that path> to put it back. The heightmap is indexed [x, y] with x = world X. Applies unless preview=True: snapshot_project first (only the heights are backed up, not layers or objects). Not saved (save_level); the ground draws black or flat-coloured until terrain_layers(action='bake').
- `terrain_height(points: list[list[float]] | None = None) -> dict`
  Ground height of the OPEN level at world points [[x, y], ...] in metres (bilinear on the heightmap, from the engine's own data; the terrain starts at 0, 0): the z to give place_object / create_object so a building or a lamp stands ON the ground and not in it. Each answer says `inside` (false = outside the terrain, clamped to the edge). With no points: the terrain's numbers (samples, unit, size in metres, min / max / average height, water level, the max-height setting).
- `terrain_layers(action: str = 'list', material: str = '', texture: str = '', altitude: list[float] | None = None, slope: list[float] | None = None, repeat: float | None = None, export: bool = True, resolution: int = 2048, multiplier: float = 8.0) -> dict`
  The OPEN level's ground layers. action 'list' = the layers (index, name, material, rules). 'add' = create a layer (the editor's terrain.create_layer), optionally with a `material` (a .mtl under Assets, e.g. materials/ashvale/grass) or a `texture`, `altitude` = [min, max] metres and `slope` = [min, max] degrees (the layer shows only there). 'bake' = paint every layer into the terrain's colour texture (generate_surface_texture: reports the measured coverage per layer, a layer near 0 % never opened) and, with export=True, compile it at `resolution` (power of two, 512..16384) with brightness `multiplier` (export_texture: WITHOUT IT a created level's terrain is BLACK). Not saved (save_level). Check the result by looking: debug_view / take_screenshot, or compare_shots.
- `vegetation(action: str = 'list', mesh: str = '', index: int = -1, spacing: float = 8.0, size: float = 1.0, size_var: float = 0.0, min_alt: float | None = None, max_alt: float | None = None, min_slope: float | None = None, max_slope: float | None = None, area: list[float] | None = None, params: dict | None = None) -> dict`
  Vegetation brushes of the OPEN level (trees, grass, rocks painted over the terrain). 'list' = the brushes (index, mesh, density, size, rules, instance count). 'add' = a brush from a `mesh` (.cgf path under Assets, the GameSDK sample's paks or the engine's, e.g. objects/natural/trees/ashvale_pine.cgf; the path is CHECKED FIRST, the engine makes a broken brush for a mesh that failed to load and nothing removes a brush); spacing = average metres between instances (smaller = denser), size/size_var, and min_alt/max_alt (m) / min_slope/max_slope (degrees) where it may grow. 'paint' = scatter brush `index` over `area` = [x1, y1, x2, y2] in world metres, honouring its rules; 'clear' = remove its instances there. 'params' = change brush `index` with `params` {size, sizevar, density, bending, airadius, hideable, castshadow, elevmin, elevmax, slopemin, slopemax, hidden}. Not saved (save_level).

- `read_asset_file(path: str, max_chars: int = 20000) -> str`
  Read a text asset of the loaded project by game path, loose or packed, e.g. "Scripts/AI/Navigation.xml", "Scripts/AI/Factions.xml", "Scripts/AI/BehaviorTrees/SDK_Grunt_03.xml", "Libs/EquipmentPacks/AI_Rifle.xml".
- `texture_recipes() -> dict`
  The procedural surface recipes make_texture can produce: bark, plaster, timber, thatch, stone, slate, planks, cobble, dirtroad, cloth, each with the metres one texture tile should cover and whether it also gets a height map (for offset bump / parallax occlusion).
- `make_texture(surface: str, name: str, size: int = 512, folder: str = 'textures/generated', overwrite: bool = False) -> dict`
  Make a tileable texture set (diffuse BC1, normal+gloss BC5, and for most recipes a height map BC4) from a procedural recipe and compile it with the ENGINE'S OWN rc.exe into Assets/<folder>/<name>_diff|_ddna|_displ.dds. surface: see texture_recipes. folder must be under textures/. Takes 10-60 s. The height map's BC4 format is verified (RC picks BC3 for any TIFF with alpha unless the preset is inside the file; this handles that). Returns the files with their real formats, the lint result, and the 'material_texture' to pass to write_material.
- `write_material(path: str, submaterials: list[dict], overwrite: bool = False) -> dict`
  Write an Illum multi-material .mtl at Assets/<path>.mtl ('materials/<folder>/<name>'). submaterials, IN INDEX ORDER (a mesh stores the index: append, never reorder): [{name, texture?, tint?, shininess?, surface_type?, height_depth?, tiles?, glass?, metal?}]. texture: 'textures/<folder>/<name>' as make_texture returned it (diffuse + normal, and the height map when height_depth is given). height_depth: 0.01-0.05 turns on offset bump mapping (Low/Medium spec) AND parallax occlusion (High spec): GenMask 88020081 and a Heightmap slot. glass: true makes it nearly transparent (opacity 0.08), so you can see through a window. tint 'r,g,b'; with no texture the material is a flat colour. surface_type e.g. mat_wood, mat_rock, mat_glass (the types SurfaceTypes.xml defines: mat_soil, not mat_dirt). metal: true follows the manual's PBS rules (pbs_check S005): Diffuse near-black and the tint is the SPECULAR colour in linear (iron '0.55,0.54,0.52', gold '1.0,0.71,0.28'). The result is linted (textures exist, flags agree with the Heightmap slot) and says whether the shader cache is affected.
- `build_mesh(spec: dict, overwrite: bool = False) -> dict`
  Build a static mesh (.cgf) from a description, through a binary FBX and the engine's own rc.exe, with metric UVs so a texture keeps its scale. spec = {name, folder? (default objects/generated), material_file: 'materials/<folder>/<name>' (the .mtl the mesh names), materials: [names in the .mtl's sub-material order], tiles?: {material: metres one texture tile covers}, parts: [...]}. Each part has a 'material' and exactly one shape, in metres (x right, y forward, z up): {box: [x0,y0,z0,x1,y1,z1], faces?: '-x +x -y +y -z +z'} {bar: {a, b, half_width, half_thickness, plane_normal?}} {quad: [p0,p1,p2,p3], flip?, uv?} (counter-clockwise seen from outside) {cylinder: {center: [x,y,z_bottom], radius, height, sides?}} LEVELS OF DETAIL (the engine's own mechanism, from the manual's LODs page: child nodes named $lodN_<name> under the base mesh, which RC puts into the .cgf; the engine has NO LOD generator, so they are authored): spec 'lods': 1-3 extra levels; a part's 'detail': N leaves that part out of LOD N and every coarser one; a cylinder halves its sides per level (not below 6). Each LOD should save about half the triangles. Verified in the engine: with e_LodMin 1 the detail parts are gone from the picture. A folder name containing '_lod' is refused by the engine ("'_lod' meshes can be loaded only internally"): never name a folder zz_lod. The result reads the material name BACK from the compiled .cgf, measures the compiled mesh's real size against the spec, reads the LOD nodes and their triangle counts back (`lods`, `lod_warnings`), checks the .mtl exists and covers every material id used, and lints. ok=false lists what is wrong (a missing .mtl draws flat grey: write_material it). Place the mesh in the level with the editor's own object tools (or Prefab='<game_path>' in a layer), then shoot_game to look at it.
- `asset_info(path: str) -> dict`
  What the engine's asset system recorded about one asset (the `.cryasset` file next to it): its type, GUID, the files that make it up (a mesh's LOD chain), what it measured (triangle and vertex counts, material and texture counts, a texture's width/height/mips) and what it DEPENDS ON, plus what other recorded assets depend on it. `path` is relative to the project's Assets folder, or a GUID. Reads files only; works with the editor closed. An asset the engine has not generated metadata for is reported as such (asset_report('coverage') says how many).
- `asset_report(report: str = 'summary', type: str = '', limit: int = 15) -> dict`
  Questions about the project's assets answered from the engine's own metadata. report: 'summary' (assets by type, dependencies recorded) | 'coverage' (real asset files, by extension, that NO metadata covers: the engine has not recorded them) | 'heaviest' (the biggest of `type`: Mesh by triangles, Texture by pixels; default Mesh) | 'unused' (assets of `type` that no recorded asset depends on; default Material: a level layer may still use them, this does not read layers). Reads files only; works with the editor closed.
- `asset_metadata(apply: bool = False) -> dict`
  Create the MISSING `.cryasset` metadata files with the ENGINE'S OWN pipeline: the Asset Browser's Edit > Generate/Repair All Metadata (the manual's 'Generating Metadata'), which the launcher's `metagen` action also runs: Tools/rc/rc.exe /job=Tools/cryassets/rcjob_cryassets.xml /src=<Assets>. The job REPLACES existing metadata (a new random GUID each time), so it is run with /targetroot into a scratch folder and only the files that do not exist yet are copied into the project (apply=true); an existing file is never touched. The `_lodN.cgf` files get none by design (part of their mesh). apply=false (default) is a dry run: how many it would create, by type, with examples. Afterwards asset_info and asset_report('coverage') cover every cgf/dds/mtl (what stays without metadata: the .adb and .bspace, which have no asset type). The metadata is for the editor's Asset Browser and the dependency queries; the game does not read it and the packager leaves it out. Writes only new files; nothing is overwritten, so no snapshot is needed.
- `pfx_write(path: str, components: list[dict], overwrite: bool = False) -> dict`
  Write a particle effect (.pfx, the engine's JSON format) under Assets/Particles from a plain description, then LOAD it with the engine's own loader (the editor must be open) and report what the engine kept. Every value starts from the engine's DEFAULT for that feature (particle_info shows them); a feature or parameter the engine does not have is REFUSED up front, with the nearest names, instead of being silently dropped. components: [{"name": "embers", "parent": "", "features": [{"feature": "Spawn: Rate", "params": {"Amount": {"value": 80}}}, {"feature": "Render: Sprites", "params": {"FacingMode": "Camera"}}, {"feature": "Appearance: Material", "params": {"Texture": "textures/sprites/glow/glow_a.dds"}}, {"feature": "Appearance: Opacity", "params": {"BlendMode": "Additive"}}]}]}. A component needs a Spawn, a Life and a Size feature and may enable only one Life/Motion/Render feature (the engine switches a second one off: engine_check.disabled_by_engine). A parameter with modifiers is {"value": 0.35, "modifiers": [{"Random": {"Amount": 0.4}}]} (a colour parameter calls the list "Modifiers"). path: 'Particles/<folder>/<name>.pfx'. Never replaces a file unless overwrite=True; the editor's CryPak caches a loose asset, so use a new name instead of overwriting. Then look at it with pfx_preview.
- `rc_presets(text: str = '', file_name: str = '') -> dict`

- `take_screenshot(filename: str = '') -> dict`

- `shoot_game(shots: list[str], build: str = 'release', time_of_day: float = 12.0, allow_editor_close: bool = False, wait_seconds: int = 180, max_width: int = 960) -> list`
  SEE the game: launch the packaged build, place the player at each spot, and return the pictures (the game window's own pixels, 1280x720, UI included). Each shot is a line: 'label x y yaw [z]' (yaw 0 looks north +y, 90 west, -90 east, 180 south; z is the feet, default terrain+0.1; the camera is 1.6 m up), 'label house:<Name>:<S|N|W|E>:<metres>' (that side of a house, looking at it), '!console command' (run it, wait 3 s), '~console command' (no wait), '=label' (a picture where the player stands now). - `get_shots(job_id: str, names: list[str] | None = None, max_width: int = 960) -> list`
  The pictures of a finished shoot job (shoot_game's job_id), optionally only the named labels.
- `compare_shots(a: str, b: str, control: str = '', region: list[float] | None = None) -> list`
  Compare two pictures of the game by measurement. a, b, control: '<job id>:<label>' (a shoot job's picture, see shoot_game / list_jobs) or a path under job_runs. CONTROL = a second capture of the UNCHANGED view that `a` shows: the game never draws the same frame twice (the night sky moved ~19 levels between two captures of one view, grass ~4, a stone wall under 1), so without it a difference means nothing: the verdict then says the noise floor is unknown. With it, each cell of a 4x4 grid is judged against its own repeat difference, and the answer says WHERE it changed (e.g. the lamp pool at a door) and how many times the noise. Returns the measurements (mean abs diff, changed fraction, luminance, local contrast = the stipple measure, per-cell values) and a difference picture: red = cells changed beyond noise, blue = differences that are within it. region [x0,y0,x1,y1] as fractions restricts everything to that part. A picture compared with itself is always measured and must read exactly 0 (the instrument's own control).
- `debug_view(views: list[str], eye: list[float] | None = None, target: list[float] | None = None, width: int = 640) -> list`
  LOOK at the level through one or more engine debug views, in the EDITOR viewport (the game is not run): for each id from debug_views ('render:Normals', 'render:Albedo', 'render:wireframe', 'environment:e_Fog'...) the variables are set, a picture of the Perspective viewport is taken, and every variable is put back and READ BACK (`restored` must be true). A picture 'plain' with no view is added first as the control. eye / target: world positions [x,y,z] for the camera (default: where the editor camera is now, looking along it). Up to 6 views per call (each costs ~7 s). The editor accepts the cheat and const variables these use; a Release game would refuse most of them. Needs Sandbox open with the level; changes nothing in the level.
- `visual_check(accept: bool = False, inject_fault: bool = False, calibrate: bool = False, allow_editor_close: bool = False, wait_seconds: int = 420) -> list`
  Visual regression (the Ashvale example project's 20 fixed views and ONE global baseline; accept=true REPLACES that baseline, so snapshot_project first): does the packaged game still LOOK the way it was accepted? Captures 20 fixed views (the green, the village, the roads, the camp, the nine houses by day; chapel, tavern, a cottage, the smithy, the green and the camp at 22:00), each TWICE in a row, and compares each with the accepted baseline picture. The two captures of one view are the noise floor (sky, swaying grass, a villager walking by): a view counts as changed only where it differs from the baseline clearly more than from its own repeat. Returns the verdict per view (where it changed and by how many times the noise) and difference pictures of the changed ones (red = beyond noise, blue = within it). accept=true stores this run as the new baseline: do it once, on a package you have looked at and approve of, and again whenever a change is MEANT to alter how things look. inject_fault=true darkens the picture by 30 percent: the day views must be flagged (it proves the harness can fail). It closes the editor and launches the game (~3 minutes): needs allow_editor_close=true, so tell the user first. It shows the PACKAGE: package first (health_check says if it is stale). The same unchanged game differs from launch to launch (trees, the near ground, the sword's sway): the render is made as deterministic as it can be (grass off, SMAA without temporal filtering, no volumetric clouds, each setting verified), the HUD is masked, and what is left is LEARNED: calibrate=true adds one launch of the UNCHANGED game (same package as the baseline, else refused) to a per-cell tolerance. After accept, run calibrate a few times (3 or more); a cell is then flagged only if it exceeds what unchanged launches showed there. It sees visible regressions (a house gone grey, a texture missing, light that moved), not small tuning.
- `visual_status() -> dict`
  The visual baseline without running anything: when it was accepted, how many views, how old the package it was taken from was, whether the current release package differs from it (health.package_freshness), and the last visual_check's result. No baseline yet means: run visual_check(accept=true) once.
- `pfx_preview(effect: str, position: list[float], distance: float = 6.0, wait_s: float = 4.0) -> dict`
  Look at a particle effect in the EDITOR viewport (the game is NOT run): a control picture of the view, then a scratch entity with a Particle Emitter component at `position` (x, y, z metres; put it a little above the ground) is given the effect, a picture is taken after wait_s seconds, and the entity is deleted (the object count is checked; a graceful editor close would save a leftover). The camera looks at the emitter from `distance` metres to its south. Returns the picture, the pixels that changed against the control, their mean colour (and the control's there), the noise between two control pictures, and the component the engine used. A bright effect is bright against the background: a DARK result usually means a texture meant for additive blending drawn with Alpha. effect: 'particles/<folder>/<name>.pfx'.
- `render_tour(settings: list[str] | None = None, eye: list[float] | None = None, target: list[float] | None = None) -> dict`

Returns per setting: the mean grey-level difference, the share of the picture that changed and where (3 x 3 grid), the `drift` (how far the UNCHANGED view moved since the previous control: shadows, streaming and eye adaptation make the scene drift after some switches) and `ratio` (difference over the larger of noise and drift: below 2 means 'cannot tell', above 10 is plainly visible), the picture, the engine's own help text as label, and `restored`. Needs the editor open; takes about 20 s.

- `snapshot_project(label: str = '', note: str = '', full: bool = False) -> dict`
  Back up the active project (Assets, Code, config) into a content-addressed store in _snapshots next to the project folder (override with CRYENGINE_SNAPSHOT_DIR). Opt-in extras can add the plugin source, the engine repository's git diff and a Claude memory folder (private notes: do not share such a snapshot). Incremental: each distinct file content is stored once, so a snapshot after a small change stores only what changed. Take one BEFORE anything that deletes, overwrites or rebuilds in bulk (a prefix delete, a regenerate, a restore, a refactor); a project under git does not need it. Build output, CI/job runs, generated solutions, logs and editor .bak files are left out (regenerable). The store is on the SAME disk as the project: it protects against mistakes, not a failed drive (copy it elsewhere, or restore '**' to a folder on another drive). Nothing ever deletes a snapshot. Files the editor holds locked are listed as skipped; files that changed while read as unstable (take it again with the editor idle). full=true re-hashes every file (the fast path trusts size + modification time).
- `list_snapshots(limit: int = 20, verify: str = '') -> dict`
  The snapshots, newest first (id, time, label, files, size, megabytes it added), where the store is and how big it is. verify='<id>' re-hashes every stored file that snapshot refers to and reports any that is missing or corrupt.
- `diff_snapshot(a: str, b: str = 'current') -> dict`
  What differs between snapshot `a` (an id, or 'latest') and snapshot `b` or the live files ('current', the default): files added, removed and modified, with the first names. Paths are as the snapshot stores them: 'project/Code/Components/Npc.cpp', 'docs/notes.md', 'plugin/...', 'memory/...', 'engine/local_changes.patch'.
- `restore_files(snapshot: str, paths: list[str], to: str = '', overwrite: bool = False) -> dict`
  Get files back from a snapshot. paths: exact snapshot paths or globs ('project/Code/**', 'project/Assets/levels/ashvale/layers/main.lyr', '**' = everything; diff_snapshot prints the exact names); a pattern that matches nothing is reported. Default: into a side folder (_snapshots/restore/<id>_<time>, or `to`), the live files untouched: compare, then copy. overwrite=true puts them back WHERE THEY WERE and replaces what is there, but first takes a snapshot named before_restore, so the restore can itself be undone (the result says which). Note: overwrite=true with '**' also writes back every non-project part of the snapshot (docs, plugin source, memory notes) where it was; list the paths you mean. Each file is checked against its hash as it is written; a corrupt stored copy aborts. With the editor open, restore level files with it closed (it keeps its own copy).

- `lint_assets(scope: list[str] | None = None, max_findings: int = 60) -> dict`
  Check the project's loose assets for the mistakes that have cost this project days, in about a second, without the editor. scope: any of meshes, materials, textures, audio, level, xml, shaders, animations (default all). Newer codes: L013 (info) meshes of 1,000+ triangles with no LOD, L014 a layer places a mesh whose path contains '_lod' (the engine refuses it), L015 a Mannequin .adb names an animation that does not exist, L016 an .adb fragment its FragDef does not declare, L017 a material's SurfaceType that Libs/MaterialEffects/SurfaceTypes.xml does not define (the engine falls back to mat_default: mat_flesh on 36 materials, mat_rock on 10, mat_cloth, mat_glass, mat_dirt). Findings carry a code: L001 a .cgf names a material that does not exist (renders flat grey), L002 a mesh uses a sub-material index the .mtl lacks, L003 a .mtl names a missing texture, L004 an XML does not parse (a '--' inside a comment: RC skips it and the packager ships a STALE copy), L005 parallax/offset-bump flags without a Heightmap slot (or the reverse), L006 a texture in the wrong format (_displ must be BC4, _ddna BC5) or not a power of two, L007 a .wav/.mp3 under audio/ (never packaged: use .ogg), L008 an audio event naming a missing sample, L010 a level layer naming a missing mesh/material, L011 the shader cache is older than a material or texture (regenerate it, then run the shader tour). Returns {ok, errors, warnings, checked: {what: how many}, findings: [{severity, code, path, message, fix}]}. A clean result lists how many files and references it actually examined: a zero with nothing examined means nothing.
- `gametoken_check(level: str = '') -> dict`

Returns libraries, references and findings (G001-G010: error/warn). A level without a GameTokens folder is a fact, not a fault. level: the folder under Assets/levels; empty = the level the editor has open.
- `pfx_check(path: str, keep_engine_version: bool = True) -> dict`
  What the ENGINE holds of a particle effect file: the editor loads the .pfx with the engine's own loader and saves it back, and this compares the two (the editor must be open; the game is not run; nothing is replaced: the engine's rewrite goes to engine_data/pfx_scratch). `dropped`: features, modifiers and keys the engine did not recognise or whose names changed between versions: SILENTLY ignored, the parameter falls back to its default (the project's own dust/leaves/rain.pfx carry such keys); `changed`: values it clamped; `disabled_by_engine`: a second Life/Motion/Render feature in one component; `defaults_added`: parameters it filled in. Control: a file the engine wrote itself loads with no difference. A file of a version below the engine's (13) is CONVERTED while loading: its 'dropped' list then includes entries that were moved, not lost (see `note`). path: absolute or relative to the project.
- `sequence_check(path: str) -> dict`

Returns the nodes, their tracks and key counts as the engine sees them, and what it DROPPED (an unknown attribute, a node of an unknown type: the whole node and its tracks vanish) or CHANGED (an unknown track parameter becomes 'Unknown Entity Parameter'; a key value that is not a number). Numbers are compared as numbers (the engine writes 512 for 512.0000). `warnings`: keys after the sequence's end (the engine keeps them; they never play). The game's hand-written intro (libs/ashvale/sequences/ashvale_intro.xml) passes: 1 node, Position + Rotation, 15 keys each, 13 s. path: absolute or relative to the project.
- `nav_reach(origin: str | list[float], targets: list[str | list[float]], agent: str = '-') -> dict`

Returns, per target, `reachable`, the mesh volume each end lies in (-1 = none), whether it is inside a volume, and a mesh ray cast. agent: an agent type name (default the first: 'Villager'). It does NOT know dynamic obstacles or OFF-MESH links: this project cuts every house door out of the mesh on purpose (a <House>_DoorCut area) and crosses it with the FarmGate's off-mesh link, so a house interior is an island here by design; the outdoors, doorsteps and open-sided buildings (barn, smithy) are what this answers. Controls that hold: start -> BanditYard connected; a point 3 km away is not.
- `nav_map(x0: float, y0: float, x1: float, y1: float, step: float = 5.0, z: float | None = None, origin: str = '') -> dict`

One character per `step` metres, z = the height the cells are tested at (empty = the origin's own z; the example village's floor is about 36.3-36.5). At most 4000 cells.
- `bt_check(tree: str = bt_mod.DEFAULT_TREE) -> dict`

Measured: an unknown node type, a transition to a state that does not exist, a condition on an undeclared variable, an invalid structure and a GameSDK GameDll node (Melee, Shoot ... not loaded by this game) REFUSE the tree; an unknown ATTRIBUTE and a value that is not a number are accepted silently (the engine holds 0), and an event nothing sends is only a warning ('declared automatically'): the comparison with the file finds the first two. Also compares the events the game's C++ sends (SendBehaviorTreeEvent) and the blackboard keys it writes (BlackboardVariableId) with what the tree declares, handles and reads. tree: a file path, or a name in Assets/scripts/AI/BehaviorTrees (default Villager_Patrol, which passes). Nodes the engine cannot describe (Basic_MoveToPosition comes back as a bare <Node>) are listed in `not_comparable`.
- `uqs_check(query: str = uqs_mod.DEFAULT_QUERY) -> dict`

Loading registers a material in the editor's library for the session; no file is changed.

- `level_check(level: str = '') -> dict`
  The level's SETTINGS and its EXPORTED copy against what the engine reads, without the game. - `frame_profile(frames: int = 240, compare_cvars: dict[str, str] | None = None, top: int = 10) -> dict`
  Where the CPU time of a frame goes, per thread and per function, from the ENGINE'S OWN frame profiler (the boot profiler: `sys_bp_frames <n>` records the next n frames as bp_frames.xml in user/TestResults, the file ProfVis.exe opens), on the OPEN EDITOR's viewport, without the game. Needs the editor; switches the profiler on and keeps the editor active for about a second per capture (a long hold can crash a graphics driver), then puts both back. 240 frames are about 1.2 s: enough to catch something that happens once a second. Returns the summary (main-thread ms per frame, median and longest frame, the `top` functions by SELF time with ms per frame, calls per frame and how many threads ran them) and findings: P001 the frame time and the largest cost, P002 log writes (CLog::LogV) inside the frame, P003 HITCH frames (much longer than the median) with the functions that made them so, P004 how long the render thread waited for the main thread. compare_cvars {'e_MergedMeshes': '0'}: captures the state as it is, with the variables set, and as it is again (the REPEAT is the noise a difference must exceed 3 x) and returns what changed per frame, the variables put back. Observed on the author's Ashvale example with CRYENGINE 5.7.1 on Windows: it found a once-per-second hitch caused by lamps writing trace lines. This is the EDITOR's frame, not the shipped game's: use it to compare states and to find work that repeats.
- `visarea_check(level: str = '', probes: list[list[float]] | None = None) -> dict`
  The level's VIS AREAS, PORTALS and OCCLUDER AREAS as the 3D ENGINE holds them (plugin verb bridge.visarea.dump: I3DEngine::GetIVisAreaManager lists every area with its name, flags, box, shape points and the areas it connects), against the layer files and the exported level pack's terrain/indoor.dat, without the game. The manual says objects inside a Vis Area are not drawn from outside, a Portal cuts an entrance, a closed area is invisible from outside; the ENGINE adds rules it does not state (VisAreaMan.cpp UpdateVisArea): (1) an area is classified by a WORD IN ITS LOWER-CASED NAME: 'portal', then 'visarea', then 'occlarea', and a name with none of them is kept in NO list (a VisArea called Reeve_interior silently does nothing; one called visarea_portal_room is a portal; the editor adds 'Portal_' / 'OcclArea_' to a Portal's / OccluderArea's own name, so those always classify); (2) the editor registers an area only with MORE THAN 3 points; (3) a portal connects areas only when its first 4 points form a quad whose opposite edges cross a wall of the area, 1 connection = to the outdoors, 2 = room to room, more is invalid. V001 name not classified as its kind (error), V002 under 4 points (error), V003 portal that connects nothing (warning), V004 vis area no portal reaches (closed: warning), V005 portal with 3+ connections (error), V006 layer object the engine does not hold, V007 the exported pack's counts differ from the layer (stale export, error), V008 engine area no layer object explains, V009 the level has no areas at all (information), V010 portal with more than 4 points. probes: [[x,y,z], ...] positions to look up: the area that contains each (the engine's GetVisAreaFromPos after forcing its tree to rebuild, and the direct per-area test; both are null/empty outdoors). With the editor closed only the file checks run. create_object warns when a new area's name will not be classified.
- `object_check(level: str = '') -> dict`
  The level's NON-ENTITY objects (brushes, navigation areas, environment probes, shapes ...) as the open EDITOR kept them against the layer files (layers/*.lyr), without the game: the sibling of entity_check. Each object reads the attributes it knows from its node when the level loads; a name it does not know is IGNORED WITHOUT A MESSAGE, an unreadable value leaves the default, an out-of-range value is clamped. `bridge.object.xml` writes the live object back through the same serializer; this compares attribute by attribute (numbers within 0.001, comma lists member by member) and child by child: O001 an object the editor does not hold (error), O002 an attribute in the file the live object does not have (warning: ignored), O003 a value that differs (warning, both shown: clamped, not read, or another type), O004 an attribute only the live object has (information: the file predates it), O005 a child node that differs, O006 the editor's object count differs from the layer files' (information), O007 a name used twice. A component's instance `guid` is NOT compared: the editor makes a new one at every level load. Needs the editor with the level open.
- `entity_check(level: str = '') -> dict`
  The level's ENTITIES and their components' properties as the running ENGINE kept them, from the open editor, without the game. A layer file (layers/*.lyr) stores each entity's class and, per component, a <properties .../> element; when the level loads, a property the component does not have (a typo, or a member renamed in the C++ Reflect) is IGNORED WITHOUT A MESSAGE, an unregistered component type is dropped, an unregistered entity class makes no entity, and an unreadable value leaves the default. bridge.component.properties serialises each live component with the engine's own serialization; this compares it with the layer: N001 an entity the editor did not load (error), N002 a component the live entity lacks (error; the engine's own list of the ones it has), N003 a property in the file the component does not have (warning, says what it has), N004 a value that differs (warning, both shown; nested structures such as MeshScale are compared member by member), N005 an editor entity no layer holds (information), N006 not compared (legacy Lua <Properties>, a component type twice, a name with a space). Unsaved edits in the open editor show up as N004. level: the folder under Assets/levels; empty = the level the editor has open (a fixed level name would make every object read as missing while another level is open).
- `pbs_check(paths: list[str] | None = None, include_imports: bool = False) -> dict`
  MATERIALS against the manual's PHYSICALLY BASED SHADING rules (no editor, no game; about 1 s): S001 a Diffuse colour channel above 1.0 (an albedo above 100%), S002 a textured material whose Diffuse colour is not 255,255,255 (the manual keeps it white and puts the colour in the texture), S003 a non-metal whose Specular colour is outside sRGB 40..60 (error above 80, 'never higher'), S004 a Specular colour that is not white while a specular MAP is used (it multiplies the map), S005 a metal (surface type mat_metal*, a metal name, or Specular above 150) whose Specular is below sRGB 180 or whose Diffuse is not black/very dark, S006 Shininess below 255 with a _ddna normal map, S007 a coloured Specular on a non-metal. The engine's own shader settles what Smoothness means (Illum.cfx: attribs.Smoothness = MatSpecColor.w * GetSmoothnessTex(...)): the FINAL smoothness is the material's Shininess/255 TIMES the alpha of the _ddna map, so Shininess 50 with a map scales the map to 20% of itself (a material without a map uses the slider alone). Only the Illum shader is judged. The findings are deviations from guidelines, not bugs. include_imports adds the GameSDK materials under Assets/objects.
- `project_audit(details: bool = False, editor_free: bool = False, accept_baseline: bool = False) -> dict`
  ONE CALL that runs every engine-owned validator of this server over the project (about 5 seconds with the editor open, no game): asset lint, Crytek's own 144 unit tests, the PBS material rules (advisory: its errors count as warnings), the audio libraries against the code, the time-of-day presets, and, from the open editor, the engine's own loaders for materials, characters, Mannequin databases, the behaviour tree, the UQS query, flow graphs, the Dynamic Response System, the character animation data, the .cryproject files, the Track View sequence, the particle effects and the editor's 'Check Level for Errors'. Use it before packaging, after any asset or code change and after an engine or driver update..
- `env_check(paths: list[str] | None = None) -> dict`
  ENVIRONMENT PRESETS (.env) against the rules of the engine's own loader, without the game or the editor. How a version-4 file is read (EnvironmentPreset.cpp:627): POSITIONALLY, the i-th <var> into variable i, so a missing, extra or reordered <var> shifts every later variable with no error; an older file is converted by id; every evaluated spline value is CLAMPED to the file's minValue/maxValue. Findings: E001 not a preset, E002 older version (converted), E003 the <var> sequence differs from the engine's 145 (misload), E004 a key value outside the range (clamped: never reached), E005 key times outside 0..144000 or out of order (a day is 144000, 6:00 is 36000), E006 a colour with keys in red and none in green/blue, E007 the file's range differs from the engine's table, E008 no Constants block. A known case: PARAM_NIGHSKY_MOON_COLOR_MULTIPLIER is 0.4 in the engine's own template while its range ends at 0.1, so the engine uses 0.1. paths: relative to Assets (default every .env in libs/environmentpresets). Note: the editor's CURRENT preset is the engine default (%ENGINE%/EngineAssets/Shading/default.env) after a restart; the game can switch presets itself.
- `env_diff(a: str = 'libs/environmentpresets/ashvale_clear.env', b: str = 'libs/environmentpresets/ashvale_rain.env', hours: list[float] | None = None) -> dict`
  Which time-of-day variables DIFFER between two presets, sampled at hours of the day (default 0, 6, 9, 12, 15, 18, 21; linear between keys, the engine uses Bezier with the stored tangents, so values are approximate but a difference is real). Each entry gives the variable, its group, at how many hours it differs and the two values at each such hour.
